A device grid for the kit, and one set of value marks

Your ask: a grid for values as a standard kit element, <luma-device-grid>, so the device sheet is its first user and not its only one. And the programmer must show the same coloured indicators. This page proposes the element, the anatomy of a value cell, and the marks as kit tokens. It then shows the same marks on every surface where a value appears.

Question 1 · Where the value grid lives

Your proposal is a <luma-device-grid>. Three ways to build it:

A · your proposal, recommended

<luma-device-grid> extends <luma-grid>

A kit element of its own (kit/devicegrid.js, class LumaDeviceGrid extends LumaGrid). Rows are devices, columns come from the attributes of the patched types in scope. It adds what only devices need: feature-group headers over attribute columns, folder rows from the patch tree, the value cell, the layer switch, merged cells, the Channel / Dimmer+ tile views and the values feed.

  • It inherits the grid's selection (+ / − / Thru / lasso), keys, the one context menu, the pointer core, virtual scroll for the rig's 1 348 rows, frozen columns, column sets and the miniature. So “every list of objects is <luma-grid>” still holds.
  • One place for device code: the device sheet, the programmer view, the preset editor and the patch dialog's live column all use it.
B

A value column kind inside <luma-grid>

No new element: the plain grid gains kind: 'value' columns and a second header row.

  • Least code; any grid can show a value column.
  • The device-only parts (attribute columns per type, tiles, layers) end up as switches inside the general grid.
C

A separate element on its own scroller

Built for devices from scratch.

  • Free to be fast in its own way.
  • Two grids to keep in step: selection, keys, menu, miniature, column sets.

In every option the value cell and its marks are one kit module (kit/marks.js, question 3), so the encoder bar and the programmer draw the same marks without a grid. The sequence track sheet's rows are cues, not devices; it uses the plain grid with value columns from the same module.

The value cell

One cell, four layers of meaning, each in its own place, so they never fight:

  • Text colour: where the value comes from (default, which sequence, new / tracked / blocked).
  • Background: what is happening to it (in the programmer and active; fading).
  • Indicator bar along the top: which layers hold data (absolute, relative, fade, delay, phaser, preset, park). Deactivated programmer data is white on the left; DMX tester data is white on the right.
  • Symbol on the left: the mixed colour or the gobo. A fade progress line runs along the bottom while fading, like the sequence miniature's running cue.

Question 2 · Which colours

The meanings are the established ones (solid red = an active programmer value); the question is the paint. In A the marks copy the usual console colours. In B they become kit tokens: the kit already has Programmer for programmer values and Park for parked channels, and every theme (Dark, Daylight, Night, the theme editor) restyles them in one place.

A · Console colours
B · kit tokens (recommended)

Two places where B differs from the usual colours on purpose: the programmer red is the kit's rose (--lc-programmer), so it doesn't read as an error (--lc-alert), and Park is the kit's teal instead of the usual blue, because blue is already the selection edge in the miniature. Both are one token each if you want the usual hue.

Question 3 · The same marks everywhere a value shows

Your note: the programmer must use these indicators too. Established consoles already do it on the feature-group bar and the encoders. Proposed: the marks are one kit module (marks.js + the tokens). The grid cell, the encoder readout, the feature-group tab, the attribute board's chip and a fixture's name cell all draw from it. What the grid needs from the station

One new feed on /ws/feeds, values: a Samples feed, built by lumacore-views like every other view. Per window it carries the rows and columns the window shows (its scope, page 3), and for each cell the value, the readout text and a small state record. Only visible rows stream (the grid is virtual), at the feed's rate, never from the render tick. The plan's value tier is read off the tick, which keeps invariant 10 (the tick allocates, locks and looks up nothing).

The kit rule already points at A: “every list of objects is <luma-grid>”, and a window that needs a missing element waits for its approved mockup, then the element goes into the kit and the Showroom before the window uses it.

{ fixture: "…guid", attr: "Pan", text: "−45°", sym: null,
  src: "programmer" | "sequence" | "park" | "default",
  prog: { active: true, user: 1 },          // the viewer's programmer only
  seq:  { no: 1, selected: true, cue: "new" | "tracked" | "blocked", lower: false },
  fading: 0.4,                               // progress, null when still
  layers: ["abs", "fade"],                   // the indicator bars
  preset: "4.2" }

The fields for states not built (relative, phaser, recipe, DMX tester, parts) are named now and stay empty, so the marks have their places.

To decide on this page

1. The grid: A, <luma-device-grid> extending <luma-grid> (your proposal, recommended); B, a value column kind in the plain grid; or C, a separate element?
2. The paint: A, the usual console colours, or B, kit tokens with the same meanings (recommended)? With B: keep the kit's rose for the programmer, or the usual red?
3. The marks as one kit module used by the grid, the encoder bar, the feature-group tabs, the attribute board and the programmer list: yes?
4. The cell anatomy (text = source, background = state, top bar = layers, symbol left, fade progress bottom): keep, or change a part?
