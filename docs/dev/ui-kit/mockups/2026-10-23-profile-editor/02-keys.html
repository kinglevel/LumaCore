Keys: one keyboard, every mode

The Keys tab of the UserProfile editor. A full keyboard drawn by physical key in the device's layout, a layer per shortcut mode (All modes, KBD, PRG, NAV) and per modifier (Ctrl, Alt, Meow), and for the picked key every layer that touches it, its gesture lines and what it does. The list beside it is the same bindings as rows, linked both ways: find a line and its keys light up.

Try: switch All · KBD · PRG · NAVhold Shift or Ctrl+Alt on your own keyboardRecord, then press a keyfind Storeflip the layout to ANSI · US and look at NAV's / and ?

Questions

  1. A binding belongs to a mode. Bind "S" `Store` /Shortcuts "PRG" binds in PRG only; without /Shortcuts it binds in every mode, as today. A mode's binding overrides the All binding on the same key (the blue corner). recommended This adds an option to Bind / Unbind: a syntax change, so it waits for your yes. /Shortcuts reuses the word that already names the modes; Mode is taken by a fixture's DMX mode.
  2. PRG's letters and NAV's keys become LumaCore defaults you can see and change: shipped UiKeys (prg.s, nav.y) bound per mode, instead of the two tables in the terminal. Each can be changed, moved, turned off on your profile and reset. The terminal, web and app read the same rows. recommended This also lands the old decision that NAV's cd .. / cd / are profile data.
  3. Letters: in KBD they always type and can't be bound; in PRG and NAV any key can be bound. recommended Today the rule reads "never letters", yet PRG has 13 letter keys and Bind doesn't refuse one.
  4. Where the mode lives: per device screen (two screens can be PRG and NAV), shown on the status strip as today. recommended Today it is one value for the whole station; the roadmap already lists "per screen".
  5. Keys are named by what they type (today's names: /, ö, Ctrl-r), so a binding follows the user's layout; the editor draws the device's layout from the kit's layout files and warns where Ctrl+Alt is AltGr. recommended The other way: physical positions (KeyQ), the same place on every layout, but / would move.
  6. The numpad as its own keys (Num7, NumEnter): bindable in every mode, e.g. for executors and cue numbers, while the main digits keep typing. Not in the key names today.
  7. A cheat sheet: holding F10 (or ?) shows this keyboard read-only for the mode you are in.
  8. Sharing: Export / import a key map, and "Copy from profile…" for a whole mode. Turning a LumaCore key off is stored on the profile, so Reset brings it back.

What the research found

  • Today: one shortcut mode for the whole station (PRG by default). PRG's 13 letters, NAV's ~30 keys and the line-editing keys are hard-coded in the terminal; only 8 keys are real bindings. Bindings have no mode. The terminal sees Press and Double press only.
  • Gaps: the "never letters" rule vs PRG's letters, NAV's Backspace lines decided as profile data but hard-coded, an always-empty debug layer, the web swallowing Tab before the terminal's quicksheet, the Meow key starting as Alt until the profile loads.
  • Other software: the video editors draw a full keyboard linked both ways to a command list, colour a key by its scope (app-wide / panel / reserved stripes), relabel the keyboard while a modifier is held, and list every scope of the picked key at once. None of the lighting consoles we looked at has a visual editor.
  • Pitfalls taken in: ISO keyboards (the <> key, the tall Enter), AltGr = Ctrl+Alt on Windows, a Mac's F keys needing fn, colour never the only signal (stripes, a lock, a corner, a bar).
