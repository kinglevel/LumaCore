Import MVR · 1 · drives and the library, before the file dialog

The user, on question 1's dialog: "think more broadly — in a reference console there is a drives list that links to the local library and attached external drives (HDD, SSD, USB) that can have a library structure; if a drive does not have the library path, LumaCore inits it so the user can place files in the standard file tree." So before the Import MVR dialog's shape comes where files live: what a drive is in LumaCore, where it sits in the tree, how an external drive is found and initialised, and how every file dialog (Import MVR, Insert fixtures' library, the show dialogs, Backup › Library) shows them.

The question — what a drive list needs, what LumaCore has

LumaCore today — library/README
library/
  shows/        .luma (+ .versions/ .autosave/ .trash/ — Backup §30 12d5)
  gdtf/         GDTF files to pick (Insert fixtures; browser uploads land here)
  mvr/          "MVR scene files" (empty, nothing reads it)
  media/        pictures to import; media/.store/ the hash cache
  userprofiles/ .lumaprofile    datapools/ macro/ presets/   exports
  fixturetypes/ the GDTF hash cache   logs/   stations/   station_settings.json

The tree: Root.Drives
Root.Drives = the station's whole disk ("/", C:\) — only tree-shell words
walk it (§25); `ls Root.Drives`, `rm Root.Drives.Volumes.USB.old.luma`;
no Drive object, no list, no types, no free space.

Asset drives (§30 "12a2", rewrites §8)
the show names AssetRoots (GUID + name); each station maps a root to a
folder like a network to a NIC (`Set AssetRoot "Media" "Folder" …`, station-local);
assets = root + relative path + sha256; missing ones listed.

File names on a line
`LoadShow "x"`, `Import FixtureType "y.gdtf"`: relative to the library folder
(`drive::library_file`: sub-folders allowed, no absolute path, no `..`).
What a drive must give
A name, a type (Internal, USB / external, Network, later Cloud), a mount path, free and total space, whether it holds the library tree, and when it came or went. Station-local, never replicated (like NICs and AssetRoot folders). A sysmon line when one is attached, initialised or removed.
Finding them
Linux: mounted volumes under /media/<user>/, /run/media/, /mnt/ (from /proc/mounts); macOS: /Volumes/ minus the boot volume; Windows: the drive letters with their kind (removable, fixed, remote). A watcher thread every 2 s, never the state thread; the result into StationView → the station feed, so a USB stick appears in an open dialog the moment it is in.
The tree on a drive
The same folders as the station's library under one root, LumaCore/library/ — shows, gdtf, mvr, media, userprofiles, datapools, macro, presets — minus the station's own caches and logs. Initialising = creating the folders and a README; a drive without it is listed "not initialised" and a tap (or the first write) initialises it.
Already there
Root.Drives is a Node (Disk kind) the tree shell walks; the drive door is the one way to the disk; AssetRoot's station map; the Backup › Library grid lists library/shows/; Insert fixtures' library list and its Upload. Lines name library files relative to a folder.
lum.md
A Drive object (List, Info, Set Name, Initialise, Eject?) and how a line names a file on a drive (LoadShow "x" /Drive 2, or Drive 2 "shows/x.luma") are the lum.md discussion that follows the model — question 2 of this round.

The options — the model, with the file picker and the Drives menu it gives

To decide: A, B or C. Recommended: C · the drives found by the station, plus folders you add — Root.Drives becomes the drive list: Drive 1 Internal is the station's library/, every mounted external volume is a drive the moment it is in (name = its label, type USB / External), and "Add folder…" makes a drive of any path for a network share or a folder the OS doesn't call a volume; each drive carries the one library tree under LumaCore/library/, initialised on first use, so files put there by hand are found in the standard place. Every file dialog gets the same rail: the drives, then This device (the browser upload) last; lines name a file by drive and relative path. A alone is the established model as it is, but a network share on a console is a folder, not a volume; B keeps the raw disk and makes drives a list of paths you type — no stick appears by itself, and a path is not a drive to a lighting person.
