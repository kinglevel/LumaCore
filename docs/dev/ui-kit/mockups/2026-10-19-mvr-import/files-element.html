Drives · 5 · one way to load and save files

The user: "we need a unified general way of loading/saving files." Today three dialogs list files their own way: Backup › Library (a <luma-grid> of this station's shows from the shows feed, with Load show… / Save show / Save as… / Import / Export on the slab), Insert fixtures' Library… (its own list from /api/fixture-types, Upload to library/gdtf/), and Users & Profiles' Import… (a station ask). With drives decided (C, the ids, the volume + library, /Drive), what is the one element every load and save goes through, and what does it read?

The ground — real capture, what is fixed

Decided this round
Every file dialog has the same rail — the drives, then This device (the browser upload) — and opens on the drive's library folder of its kind; crumbs jump to the whole volume and back (★ Library); a pick outside the library is copied in once; the line is <word> "name" /Drive usb1.
The kit's rules
Every list of objects is <luma-grid> (rows by key, columns from the station, selection, the lasso, the context menu); actions live in the slab; every gesture is a line; a page never polls — rows come from feeds on /ws/feeds, built on the state thread. Insert fixtures' library list and its fetch predate 12d's rule and would move onto the grid.
What a file row needs
Name, size, modified, and the kind's own columns: a show's format / saved by / versions (as today); an MVR's scene, layers, fixtures, GDTFs embedded or missing; a GDTF's manufacturer, modes; a profile's user and date; a picture's size in pixels. The station reads the file's head once and caches it by path + mtime, so a drive with 300 MVRs lists in a blink.
Save
A save is the same element with a name field under the list and the kind's folder fixed; a taken name is the station's ask (Overwrite / Keep both / Cancel), as SaveShow asks today.
The TUI
A terminal has the fence: ls ~usb1/shows, LoadShow "rig" /Drive usb1. No picker to draw there.

The options

To decide: A, B or C. Recommended: A · one kit element, <luma-files>, on one feed — the drives rail, the crumbs, a <luma-grid> of the folder's files with the kind's columns, This device, the drop, and a name field for a save; the rows come from one files feed (sub('files', { drive, folder, kind }), built on the station from a cached read of each file's head, updated when the folder changes); every file dialog is this element with a kind: Backup › Library is it at shows/ (the slab's actions stay), Import MVR's File step, Insert fixtures' Library…, Import / Export UserProfile, Import Image, and the station's "which file?" ask opens it. One element to build and test, one look, one line in the footer. B keeps three lists and adds the rail three times; C makes the picker a server-held dialog, which fits the TUI but puts a scrolling, sortable, lassoable file grid into the ask protocol that today carries buttons.
