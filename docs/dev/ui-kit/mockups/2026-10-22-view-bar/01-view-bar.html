The right sidebar: a view bar for any object, and a View pool

Three asks: a stored view button should show; a View pool window to see a profile's views; and assigning views to view buttons, later macros, sequences and any object. This page is the analysis (LumaCore's code and the established view bar) and a working mock of the bar and the pool.

Why a stored view button doesn't show

The station stores it fine; the sidebar can never match it. A profile keeps its buttons as view_buttons: BTreeMap<slot, view GUID> (step 6d's strict identity made them GUID links), but the page still looks the view up by number:

const no = viewData.buttons?.[n];                         // a GUID string
return no ? viewData.views.find(v => v.no === no) : null; // compares it to a number

So every slot draws empty (index.html:4150). A second fault: /api/views finds the profile by a name equal to your login (console_bridge.rs:595), not through your user's profile link, so anyone on a shared or differently named profile gets nothing. The bar is also an old fetch; the house rule puts it on a feed built by lumacore-views. All three go away with the build below.

The mock: dedicated pool windows and the view bar

Each pool is its own window type, spawned on its own: Views (new), Groups and Sequences (as today), Macros (new). A screen holds as many as you like, side by side; every pool window's cells can go onto a view button.

Drag a cell from any pool window onto a button, or use Assign (tap a cell in any window, then a button), or hold / right-click a button. Tap a button or a cell to run it. Every gesture shows its line below.

To decide

1. Whose buttons. Today one set per profile for every screen.
A · recommended
Per screen of the profile: ViewButton 1.4; a bare ViewButton 4 is this screen's. A two-screen desk gets two bars.
B
One set per profile, the same on every screen (today).
2. What a button can hold.
A · recommended
Any object with a default action: View, Macro, Sequence, Group, Preset, WindowPreset, ScreenConfig, User. A tap runs it as its pool tap does (Sequence: its pool action); the bar's colour and icon say the kind.
B
The established list only (views, macros, users, screen configs …), sequences and presets on executors.
3. How to assign. All three are the same line, Assign View 3 At ViewButton 1.5.
A · recommended
Drag a pool cell onto a button (the pointer core's one lift), Assign then tap-tap, and hold a button → Assign… (a pick list by kind).
B
Assign and the command line only.
4. Store on an empty button.
A · recommended
Store, then tap an empty button (or hold it): a new view of this screen in the first free number, assigned in one line, the name asked by the station's dialog.
B
Store View first, then assign.
5. A tap on an empty button.
A · recommended
Nothing changes; a hint says “Empty — hold to store this view here”.
B
Clear the screen.
6. The pool windows. Your ask: one dedicated window type per pool, never one window that switches kind.
A · recommended
Window types Views and Macros join Groups and Sequences, all on the one pool window (one element, one pools feed, a PoolDef per kind). Later Presets and others the same way.
B
Views now, Macros when Macro Store / Go are built (today only List is).
7. The View pool cell.
A · recommended
A drawn picture of the view's windows (we have their places, no screenshot needed), the screens it covers, the buttons it sits on, gold when it is this screen's view now. A window setting picks the profile: yours or any other.
B
Number and name only.
8. More buttons than fit. Your desk shows as many as fit (11 of 12).
A · recommended
As many as fit, ▲ ▼ step a set, the range shown (“1–8 of 20”); one lane now, a second lane later as a setting.
B
A fixed 8 with pages (today).
