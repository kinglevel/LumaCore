Before any rig goes in the demo: the GDTF parser refuses most of the rigs' fixture types

The 186 MVR files in ../ExternalData/BombeeRigMetadata/mvr/ were read with lumacore-mvr, and every GDTF embedded in them was fed to the station's importer (lumacore_gdtf::importer::import_gdtf_bytes, the gdtf 0.2.0 crate underneath). Two things stop a demo built from any of them today. One is fixed already; the other is this question.

Finding 1 · fixed while scanning: the number sits in FixtureID, not FixtureIDNumeric

MVR 1.6 added FixtureIDNumeric; the 183 older files (and most 1.6 exporters) write <FixtureID>4005</FixtureID> only. The crate read only the numeric tag, so every row of every real file came in without a number:

Who writes them: Capture and Depence export a stripped GDTF per type (one description.xml of 2–25 KB, primitive models, DataVersion 1.0 / 1.1) and leave out every attribute that has a default. Vectorworks embeds the manufacturer's file, which parses. The same importer on a random 400 of the 13 844 files in ../ExternalData/GDTF-DB/community: 393 parse, 7 refused (NaN colours, odd gamut points, one oversized CRI, one odd Laser geometry). So the strictness is the gdtf crate's, not a LumaCore rule, and it bites exactly the files a lighting designer hands you from the planning tools.

Capture's export of a MAC Quantum Profile, description.xml:
<Attribute Name="Dummy" Pretty="Dummy" Feature="Control.Control"/>            ← no PhysicalUnit
<DMXChannel DMXBreak="1" Offset="1" Default="0/1" Geometry="Dummy_1_1" Highlight="None">
Vectorworks' embed of the manufacturer file:
<Attribute Feature="Beam.Beam" Name="Shutter1" PhysicalUnit="None" Pretty="Sh1"/>

What to do about the parser

A · Recommended

Fork the crate into the repo and give it the spec's defaults

gdtf 0.2.0 (MIT, cpdt/gdtf-rs) copied to vendor/gdtf/, pinned with [patch.crates-io]; the seven cases above become serde defaults and lenient value parsers (NaN colour → none, a bad gamut → skipped, a bad channel set → skipped with a warning the import reports). lumacore-gdtf stays as it is (16 uses of the crate's types across 2 000 lines).

  • + a day; every refused class is one attribute with a default
  • + the lenient cases are listed in one place, testable with the stripped files as fixtures
  • − a vendored third-party crate to carry (we own it from here; upstream looks quiet)
B

LumaCore's own GDTF reader

Like lumacore-mvr: a small DOM over quick-xml inside lumacore-gdtf, reading only what the show uses (modes, channels, functions, sets, wheels, emitters, geometry names, the matrices), lenient by construction.

  • + no third-party model of GDTF in the tree; one crate per format, like MVR
  • + the long-run shape
  • − two to three days before any rig goes in the demo; the importer, channel map, validator and details rewrite with it
C

Pre-clean the XML before the crate sees it

Inject the missing attributes into description.xml as text before parsing.

  • + no fork
  • − a text rewrite of XML in front of a strict parser; brittle, and the value cases (NaN, gamut, DMXFrom) need real parsing anyway

Whatever is chosen, the stripped Capture types have no measurements and primitive models; that is fine for the demo (the console needs modes, channels and functions) and is the same data the designer's console gets.
