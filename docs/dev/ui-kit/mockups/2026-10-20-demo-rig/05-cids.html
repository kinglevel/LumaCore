Second ids: a fixture without a fixture number

You set the folders to IDType Media so they carry no FID. That reopens the CIDs question (roadmap, 2026-10-19) with a concrete case, and it has one hard consequence for LumaCore: today a fixture is its number — the patch is BTreeMap<u32, Fixture> keyed by the FID — so a fixture without one cannot exist. This page is what a second id is, what is already built, what it costs, and the one question that decides it.

Collisions are real in this rig, not theoretical: the folders' Media ids 1 … 9, 99 and 7003 are all also fixture numbers (the rig numbers 1 … 9 999). A second namespace is the only way these fixtures coexist in one patch.

Already built on LumaCore's side

  • The grammar and resolver: Fixture Houselights 4, Fixture Houselights 1 Thru 4 + Fixture 101 (lum.md "The second id"; segment = OBJECT [ id-kind ] [ ids ], LumShape::id_kinds, the second-id walk).
  • The data: CustomIdType (MVR's list: None, Fixture, Channel, Houselights, NonDim, Media, Fog, Effect, Pyro, Marker) + CustomId on every fixture; MoreIds for several; the properties "IDType" / "CID" / "MoreIds" on the Fixture object.
  • Selections and group members already hold GUIDs, never numbers (selected_fixtures: Vec<Uuid>, GroupMember.fixture: Uuid): the number is only a handle on the line.

What is not there: a fixture whose only id is a second id. Everything that reads the patch by number assumes the key is the FID:

What the pool key is, once a fixture may have no number

A · Recommended

An internal slot; the ids are a typed list

The patch stays BTreeMap<u32, Fixture> but the key is a slot given at insert (next free, stable, never shown, never on a line). A fixture's ids are one list (IdType, n): [(Fixture, 849)], [(Media, 7003)], [(Fixture, 4), (Channel, 12), (Fog, 3)]; unique per type in the show; Fixture 849 and Fixture Media 7003 resolve through one index. "IDType" / "CID" / "MoreIds" fold into it. Export writes FixtureID from the Fixture id and CustomIdType + CustomId from the first other one; import reads both back.

  • + the reference model exactly; the folders import as they are; renumbering a fixture no longer moves it in the map
  • + one door: patch.by_id(IdType, n); a tidy rule keeps fixtures.get(n) out of commands
  • − the sweep: 87 sites, the show-file folder names, format 31, the demo regenerated; about two days
B

The key stays the FID; folders get hidden numbers

A numberless fixture gets a key above the file's highest (10001 …) that is shown nowhere and written to no file; Media 7003 still needs the index of A.

  • − two kinds of key in one map; a "hidden" number leaks into List Fixture, ranges, Fixture Thru
  • − renumbering a real fixture still moves it in the map (as today)
C

The patch keyed by GUID

BTreeMap<Uuid, Fixture>, the ids a typed list as in A.

  • + the key says nothing, so nothing can lean on it
  • − breaks "all collections are BTreeMap<u32>", the folder-per-number show-file layout, every sorted list by number; a bigger sweep for the same result as A

Then, in order

  • The keyword: Fixture Media 7003 as lum.md has it, or the bare Media 7003 — one namespace rule: Effect is §28's object, Channel / Marker / Camera are words other areas want; Fixture <kind> n never clashes.
  • An untyped CustomId on import: the export writes CustomId 7003 and no CustomIdType, so the file does not say "Media". The preset gets MvrIdType (default Media) for numberless fixtures with a CustomId; the review shows "Media 7003" in the No cell; /IdType on the line overrides.
  • What a folder does to a line: Fixture Media 1 At 50 programs the subtree, the sidebar tree shows nested fixtures, Move / Delete carry children.
  • Groups from the Default pool, the show split for the tests, what is committed, the names (unchanged from page 3).
