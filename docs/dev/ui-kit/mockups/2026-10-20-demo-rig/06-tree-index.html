Facts

The order in the MVRChildren come in the exporter's own order, not by number and not by name: ACME Icarus's children 849, 852, 854, 853, 850, 851, 819, 855 … 18, 1699, 1700; ALL's folders Utills(8), Smoke(9), Pyro(5), Stage 4 layher(4), Stage 3(3), Stage 2 Keylights(2), Stage 1 Mainstage(1), Machinery(6), Previz(7). An export must write that order back; an import must keep it.
A console's indexOn the desk INDEX = NO = the fixture's own id in its type (849 for Fixture 849, 7003 for Media 7003), scoped by the parent — not a position. The order you see in the Patch is kept apart from it.
LumaCore todaypatch.fixtures: BTreeMap<u32, Fixture> flat, key = FID, shown in FID order everywhere; Fixture.Mvr.parent: Option<Uuid> (a layer, a group or a fixture) is the only tree link; layers and groups are their own numbered maps in Devices.Metadata.MVR; the grid lists fixtures.values(), so FID order.
What depends on the key87 read sites, 37 iterations, the show-file folder per fixture (Devices/…/Fixtures/<key>/). Selections, groups, presets and cues hold GUIDs; nothing stored points at a key.

How a reference console's patch behaves

A parent's children keep the file's order, and each child's index — the number in its address path — is its own id, not its position.

So there the path index is a stable id (FID or CID, by the fixture's id type; 1, 2, 3 for sub-fixtures) and the order is kept apart from it: the two are never the same thing. That is option A's shape — the id stable, an order on the node — with the one difference that LumaCore's key is a slot the line never names, because Fixture 1 and Media 1 share one flat map here.

What the tree index is

A · Recommended

A stable slot key, and an order kept on each node

The key is the next free slot at insert and never changes. Every fixture (folder or not) keeps parent and an order within its parent, spaced (10, 20, 30 …). Insert in the middle takes the midpoint; when two neighbours touch, the siblings are respaced in that one step. The sidebar, the grid's tree view and the export walk (parent, order); the flat grid can still sort by FID. Layers and groups get the same order so one rule covers the whole tree.

  • + a key that nothing ever has to rename: no show-file churn, undo and replication by GUID as today
  • + the tree is a view of parent + order, the walk is one function; the MVR's order round-trips
  • − "the tree index" is two fields, not one number
B

The key is the position: renumbered on insert

Keys are the pre-order of the tree; a fixture inserted in the middle takes that key and every key after it moves up by one.

  • + one number is the whole story
  • − every insert renames show-file folders and rewrites the map; the pre-order of a tree in one flat number means moving a folder renumbers its whole subtree
C

Nested maps, an index per parent

Fixture.children: BTreeMap<u32, Fixture>; the index is the position inside its parent; insert in the middle renumbers the siblings after it.

  • + literally a tree index, like the desk's path …99.1.7003.849
  • − the flat patch goes: every one of the 124 sites becomes a tree walk, the engine's dense slots need a flattening pass, the show file nests folders per level; the biggest sweep for the same behaviour as A
