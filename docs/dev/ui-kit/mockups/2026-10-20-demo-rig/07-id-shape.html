What ids a fixture carries

Decided so far: the patch's key is an internal slot (5), the tree is parent + order on every node (6), and a fixture "carries FID, CID and Custom type like media" (your words on 5). This page pins the shape of that, against the desk, the file and what LumaCore already has.

Facts

A reference consoleThree properties on every fixture: FID (enum FixtureIdEnum, None or a number), IDTYPE (Fixture · Channel · Universal/Generic · Houselights · NonDim · Media · Fog · Pyro · Marker · …; None on a sub-fixture), CID (enum CustomIdEnum, None or a number). One second id per fixture; the id type names which keyword reaches it. Seen: Fixture 849 = (849, Fixture, None); ACME Icarus = (None, Media, 7003); Univ = (9999, Generic, None); sub-fixture 849.1 = (None, None, None).
MVR 1.6FixtureID (text) · CustomIdType (a number into the spec's fixed list) · CustomId. One second id. The export writes CustomId on every fixture (0 where none) and no CustomIdType at all, so the type does not survive the file.
LumaCore todayMvr.custom_id_type: CustomIdType (None · Fixture · Channel · Houselights · NonDim · Media · Fog · Effect · Pyro · Marker — MVR's list) + Mvr.custom_id; Luma.more_ids: Vec<(CustomIdType, u32)> ("MoreIds", several second ids, asked for on 2026-10-19 and on the No-CIDs list to go); the writable properties "IDType" / "CID" / "MoreIds"; the grammar Fixture Media 7003 with the Fixture object's declared kinds (lum words golden: Fixture … kinds: Channel, Houselights, NonDim, Media, Fog, Effect, Pyro, Marker).
UniquenessThe reference: FIDs unique in the show; CIDs unique per id type. The rig: numbers 1 … 9 999, Media ids 1 … 9, 99, 7001 … 7009.

The id shape on a fixture

A · Recommended

The triple, exactly

fid: Option<u32> · id_type: IdType · cid: Option<u32> on the fixture (replacing the key-as-FID, custom_id_type / custom_id and more_ids). Fixture 849 is the fixture with fid 849; Fixture Media 7003 the one with (Media, 7003). FID unique in the show, CID unique per type; a folder is (None, Media, n); a sub-fixture is (None, None, None) under its fixture. "FID", "IDType", "CID" are the three properties, each a grid column. Import reads FixtureID → fid and CustomIdType + CustomId → (id_type, cid); export writes them back. MoreIds goes, its roadmap item closes.

  • + the desk's model one for one; the MVR round-trips
  • + simplest uniqueness and completion (Fixture Media <Tab>)
  • − one second id only (what the file can carry anyway)
B

A typed list

ids: Vec<(IdType, u32)>, the Fixture-typed entry being the FID; several second ids as MoreIds wanted.

  • + keeps the several-ids wish
  • − the MVR carries one; export picks the first and the rest are LumaCore-only; the desk never sees them
C

The triple, plus MoreIds beside it

A as the data the file knows, more_ids kept for extra handles.

  • − two places where "which fixture is Media 7003" can be answered; the property set and the grid grow for a wish no file or desk shares

The id-type list

LumaCore's list is MVR's (the file's numbering). The desk showed one more, Generic (the "Universal" fixture; the Univ 9999 fixture in this rig) — in the file it is a plain FixtureID 9999, so nothing is lost by keeping MVR's list; a type the console has and MVR lacks would come in as what the file writes. Recommended with A: MVR's list stays the list.
