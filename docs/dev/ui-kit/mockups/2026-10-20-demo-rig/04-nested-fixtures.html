Nested fixtures: a fixture can hold fixtures

Your direction on question 3: the tree is yours, drawn on another console with the Grouping fixture type, and LumaCore should hold nested fixtures natively so such a file imports as it is. This page lays out what that takes and asks the one thing that decides the rest: the number of a fixture that is only a folder.

What the show already has, and what it lacks

AlreadyFixture.Mvr.parent may be a layer, a group or the fixture it is a child of (MVR 1.6's ChildList, decided with 34g4 part 1). The 1 348 fixtures of the TI rig import with their parent set to the folder's GUID today.
Lacking 1The folder fixture itself: Generic@Grouping, no number, no address — the review makes it a clash row and never writes it, so 1 348 parents point at nothing and the review recreates nameless groups in their place.
Lacking 2The Patch dialog's tree sidebar walks layers and groups only (lumacore_views::patch, parent_of from mvr.groups); a fixture with children is not a node.
Lacking 3What a parent means to a line: selecting it, moving it, deleting it, a value at it.
ApartSub-fixtures (849.1, a Mini Blinder's cells, Icarus LEDs) are a GDTF geometry matter, not this tree; they stay as decided (dotted ids, Tags part 2).
The export of one folder:
<Fixture uuid="AEAC30A5-…" name="ACME Icarus">
  <Matrix>{1,0,0}{0,1,0}{0,0,1}{-100,0,0}</Matrix>          ← a position of its own
  <GDTFSpec>Generic@Grouping.gdtf</GDTFSpec>               ← 1 mode, 0 channels, 0 attributes
  <ChildList> <Fixture name="ACME ICARUS 620(CM-620Z)"> … ×286 </ChildList>
</Fixture>                                                   (no FixtureID, no Addresses)

The shape of it

  • A fixture is a fixture. A folder is a fixture of a type with no channels (Grouping, or any type), with a position of its own; its children are fixtures whose parent is it. Nothing new in the data: Fixture.Mvr.parent carries it, the world matrix stays absolute (MVR's rule), child_position is already a field.
  • The tree sidebar shows fixtures with children as nodes under their layer or group, any depth; the grid can indent or filter by the node, as the MVR tree does today for groups.
  • A line at a parent (the established rule): Fixture "Stage 1 Mainstage" selects the subtree; At 50 on it programs the children; Move / Delete carry the children (the one nesting rule, Move <node> At <node> asks, Delete asks Keep / Delete the children as MVR nodes do).
  • Import writes the folder as a fixture (new row, its type Generic@Grouping imported like any GDTF), nested; Export writes the ChildList back. Keep / Discard and the review's Lost rows work unchanged.

How a reference console holds it

A folder is a fixture whose id type is Media, with no fixture number and a second id in the Media namespace; the console reaches it as Media 7003. Numbers are global across the tree. In the MVR export the folders carry FixtureID "" and CustomId 7003 (every one of the 1 371 fixtures writes a CustomId; no CustomIdType tag, so the namespace is lost in the file). So the rule there is: a folder has no fixture number; it lives in a second id namespace (Media), and selection, Move and Delete work on it by that id. LumaCore keeps custom_id_type + custom_id as data (34g4 part 1) and has the CIDs-versus-tags discussion reopened on the roadmap.

The number of a folder fixture

Every fixture is its pool's key (BTreeMap<u32>, "a number is only its pool's key"); the file gives a folder none.

A · Recommended

A number like any fixture, given at import above the file's highest; the Media id kept as data

An unnumbered fixture gets the next free number above the highest number in the file, in a new hundred: this rig's highest is 9 999, so 10001 … 10023 in tree order (ALL 10001, Stage 1 Mainstage 10002, …). /FidOffset moves them like any row; the review shows the given number in grey. Its CustomId (Media 7003) stays on the fixture as today, so when the CID discussion lands, Media 7003 can resolve to it; Export writes the CustomId back and no FixtureID unless the operator set one.

  • + one id rule everywhere; Fixture 10002 is the whole main stage
  • + a folder can be given a real number later like any fixture
  • − a made-up number in the grid until renamed by the operator
B

A dotted id under the parent

Children keep their numbers; a folder is Fixture 1.2 under its parent, like a sub-fixture.

  • − collides with sub-fixture ids (849.1 is a cell) and the Decimal rule for cues
  • − a folder that is moved changes its id; every link to it breaks the rule "ids are GUIDs, numbers are keys"
D

The second id now: the folder is Media 7003

A folder keeps no fixture number; it is reached by its second id, which means deciding the CIDs-versus-tags question first (id namespaces in the grammar, the resolver, the grids) before the demo can be built.

  • + the file round-trips exactly
  • − the pool is keyed by number: a hidden key or a second key space either way; the reopened discussion becomes a blocker for the demo
C

No number: by name and path only

A folder is keyed by GUID, reached as Fixture "ACME Icarus" or by its tree path.

  • − the fixture pool is keyed by number; a second key space for some fixtures touches every list, grid, range and the resolver
  • − two names the same (allowed) have no second handle
